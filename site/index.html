01 / Why it exists

把“什么算对”
留在项目里。

A

分开不同种类的判断

功能验收、业务风险、视觉 token 和组件边界各归其位，后续修改更容易定位，也更不容易互相污染。

B

保留人的决定

同步器只更新受管区块。你写下的产品意图和设计判断会留在文档里，不会被一次自动扫描覆盖。

C

让事实和推断可区分

从代码能观察到的事实会被标出来；无法确认的内容保持 [待确认]，不靠想象填空。

02 / The six declarations

六份文档，
一套可继承的上下文。

它们不是一份堆满术语的总规范，而是六个各自回答一个问题的设计声明。

01BEHAVIOR

spec.md

功能为谁做？信息怎样组织？状态如何流转？什么算完成？

↗
02DOMAIN

domain.md

业务对象、术语、风险和敏感数据应该如何被表达和负责？

↗
03CRAFT

craft.md

排版、密度、状态反馈和动效怎样形成稳定的工艺感？

↗
04VISUAL SYSTEM

design.md

颜色、字体、间距、状态 token 和响应式规则的单一事实源。

↗
05COMPONENTS

components

项目有哪些真实组件？什么时候使用，什么时候不要使用？

↗
06STRUCTURE

template

页面类型、App shell、内容骨架和响应式起点如何落位？

↗

03 / The mechanism

读懂项目。
只同步事实。

01盘点

读取入口、路由、组件、样式、token 与测试。

02标记

把可观察事实写入受管区块，保留来源边界。

03收敛

根据变更文件，只更新真正受影响的声明。

managed blockpreserved by sync
<!-- design-spec:managed:start -->
## 项目事实（自动同步）
- 技术栈：`React`, `Vite`
- token：`--color-primary`, `--space-4`
<!-- design-spec:managed:end -->
